    What the data says

      Weekly trends

        Each chart has its own y-axis. Weeks start on Monday (UTC). Lead time is the median for changes that reached production that week. Failure, restore, and rework use the trailing 4 weeks so a single bad deploy in a quiet week does not read as 100%. Hover a chart for weekly values.

        Where lead time goes

          Average time per change in each stage. The four stages add up to the average lead time, shown at the end of each bar.

          Input schema

          One CSV with a header row, or a JSON array of objects with the same keys. One row per event. Times are ISO 8601. Leave columns blank when they do not apply.

          typeColumns usedMeaning
          commitid (sha), team, service, time, prA commit and the pull request it belongs to. Commits with no PR count as their own change.
          prid, team, time (opened), review_at (first review), merged_atSplits lead time into coding, review wait, review, and merge to deploy.
          deploymentid, team, service, time, env, status, kind, commits, deploymentenv: only production counts. status: success, failed, or rolled_back. kind: normal, hotfix, or rollback. commits: shas separated by semicolons. For a hotfix or rollback, deployment names the deploy it fixes.
          incidentid, team, time (start), resolved_at, deploymentTime to restore uses every resolved incident. Only incidents that name a deployment count toward failure rate.

          A deployment counts as failed if an incident names it, its status is failed or rolled_back, or a hotfix or rollback names it. To build this file from GitHub, see scripts/export_github.md in the repository.

          Runs entirely in your browser. Uploaded data never leaves the page. The team filter and sample seed are stored in the URL.
